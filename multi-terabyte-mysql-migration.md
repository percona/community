How We Migrated a Multi-Terabyte MySQL Database Without Taking Production Offline
By Paul Abiodun
When my brother's engineering team first sized up the migration ahead of them, the number that stuck with everyone was 4.2 terabytes. That was the size of the primary MySQL database powering a mid-sized e-commerce platform he worked for as a senior database engineer — a database that had grown, table by table, over nearly a decade, and had never once been moved, re-platformed, or upgraded to a new major version without some amount of downtime. This time, the business had made it clear: there would be no maintenance window. Checkout, inventory, and order tracking all had to stay live throughout.
This is the story of how that migration actually happened — the planning, the tooling, the moments it nearly went wrong, and the lessons his team took away from it. It is written from his first-hand account, with technical details checked against his own notes and run-books from the project.
The Problem With "Just Schedule Downtime"
The original database ran on aging on-premises hardware, on a MySQL version that was approaching end of vendor support. The target was a right-sized cluster on modern infrastructure, running a current, well-supported MySQL version, with Percona Server for MySQL as the engine and Percona XtraBackup and Percona Toolkit as the operational backbone.
On paper, a migration like this is simple: take a backup, restore it on the new hardware, let replication catch up, then cut traffic over during a quiet period. In practice, three things made that plan unworkable.
First, the database had several tables north of 500 gigabytes each, including an orders table that was both the largest object in the schema and the one most sensitive to locking. Second, the platform had genuine global traffic; there was no multi-hour window where write volume dropped low enough to risk a long lock. Third, and most importantly, the business had recently suffered reputational damage from an unrelated outage, and leadership was unwilling to accept any planned downtime for what they saw as "internal plumbing."
So the mandate became: migrate everything, including a live schema change on the largest tables, with zero perceived downtime for customers.
Building the Plan
My brother's team spent close to three weeks on planning before touching production, and he was adamant, when we talked about the project, that this was the single most important phase. The plan had four pillars:
1. Physical backup and restore using Percona XtraBackup to seed the new environment without locking the source database.
2. Native MySQL replication to keep the new cluster continuously in sync with production while the team validated it.
3. Online schema changes using pt-online-schema-change, from Percona Toolkit, for the handful of structural changes that had to happen as part of the move — including converting a couple of legacy tables from MyISAM remnants to InnoDB and adding new indexes the target schema needed.
4. A phased, reversible cutover, rather than a single dramatic switch, so that any single stage could be rolled back without customer impact.
Percona XtraBackup was the tool that made the first pillar possible. Unlike a logical dump, which would have taken many hours and placed real read load on production, XtraBackup performs a hot physical backup of InnoDB data files without blocking reads or writes on the source. My brother described the first full backup as almost anticlimactic: it ran in the background for a little over five hours against the 4.2 terabyte dataset, with monitoring showing no measurable increase in query latency on production. That backup was restored onto the new cluster and configured as a replica.
From there, native asynchronous replication picked up the difference between the point of the backup and live production. Replication lag was the team's primary health metric for the following two weeks; they set an internal threshold of five seconds of lag as the ceiling for a healthy replica, and used Percona Monitoring and Management to track it continuously, alongside disk I/O, InnoDB buffer pool hit ratio, and replication thread status.
The Schema Change: The Riskiest Part of the Project
The part of the migration my brother's team worried about most wasn't the data transfer at all. It was a set of schema changes that had to land on the orders table, the busiest table in the database, while it stayed fully readable and writable.
A plain ALTER TABLE on a table of that size, even on modern MySQL versions with online DDL support for some operations, still risked long lock waits for the specific changes required, including an index addition that the built-in online DDL path could not perform without a meaningful metadata lock at the start and end of the operation. Instead, the team used pt-online-schema-change, which works by creating a new, empty copy of the table with the desired schema, copying rows across in small batches, and using triggers to capture ongoing writes to the original table so the copy stays current. Once the copy is fully caught up, the tool performs an atomic rename to swap the new table into place.
My brother's account of running this against a live, heavily written table was candid about the risk. The team throttled the copy using the tool's built-in load-based throttling, pausing automatically whenever replication lag or system load crossed a threshold, so the background copy never competed meaningfully with customer traffic. Even so, they rehearsed the exact operation multiple times against a full-size copy of the database in a staging environment first, timing each run and adjusting chunk size until the copy completed in a predictable window without triggering their alerting thresholds. That rehearsal, he said, is what let them run the real thing on production with a level head instead of a live experiment.
The Cutover
With the new cluster restored, replicating cleanly, and carrying the updated schema, the actual cutover was almost deliberately unremarkable — which was the entire point.
The team moved in stages rather than a single switch. Reporting and analytics queries were pointed at the new cluster first, since those were read-only and lowest risk, and were left running there for several days to validate query plans and performance under real load. Next came read traffic from the application tier, split gradually using feature flags so that only a small percentage of read queries hit the new cluster at first, increasing over the following days as confidence grew. Only once reads had been fully and stably moved did the team schedule the write cutover: a short, controlled window, measured in low single-digit seconds rather than hours, during which the application briefly queued writes, the replica was promoted to primary, and traffic was redirected. Because every earlier stage had already been validated independently, that final step was the smallest and least eventful part of the entire project.
What Went Wrong
Not everything went to plan, and my brother was clear that the honest version of this story includes the mistakes.
The team hit one unexpected issue when the online schema change on a secondary, less critical table interacted poorly with an existing trigger the application relied on, briefly causing duplicate write attempts that were caught by the application's own idempotency checks rather than by the migration tooling. It was a reminder that pt-online-schema-change's own use of triggers can conflict with triggers already present on a table, and needs to be checked for up front rather than discovered live.
Separately, during the read traffic ramp-up, the team saw a spike in slow queries that traced back to a difference in optimizer statistics between the old and new clusters, rather than any problem with the data itself. Running ANALYZE TABLE on the affected tables after the restore, before ramping up traffic, resolved it, and it's now a standard step in their run-book for any future restore of this kind.
What the Team Would Do Differently
Asked what he'd change with the benefit of hindsight, my brother pointed to three things.
He would build in more time for staging rehearsals of the pt-online-schema-change runs specifically, since that was the step with the least margin for error and the one that benefited most from repetition. He would formalize the optimizer statistics refresh as a required step immediately after any physical restore, rather than treating it as a nice-to-have. And he would push, earlier in the project, for the phased read-traffic ramp using feature flags, which turned out to be the single most effective risk-reduction technique in the entire migration, since it let the team catch problems on a small slice of traffic before they could affect everyone.
The Result
The migration moved 4.2 terabytes of production data, restructured several large tables including the busiest table in the schema, and switched the write path to entirely new infrastructure, without a single customer-facing outage and without a scheduled maintenance window. The write cutover itself, the only stage with any true risk of visible disruption, lasted a few seconds.
For teams facing a similar project, the lessons from this one are fairly transferable: lean on physical, non-blocking backup tools like Percona XtraBackup rather than logical dumps for large datasets; treat online schema change tools like pt-online-schema-change as requiring the same rehearsal discipline as any other production-critical change, not as a shortcut around risk; and resist the urge to cut over all at once. A migration broken into small, reversible, independently verifiable stages will almost always be safer than one big move, even if it takes longer to complete from start to finish.
